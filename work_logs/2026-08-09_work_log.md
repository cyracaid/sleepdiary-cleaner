## 一、核心决策：`sleeponset` 不加自报 SOL

### 结论

```r
self_diffcalc_sleeponset = time_sleep_corrected        # 保持现状，不加 SOL
```

**splsleep 当前实现（`calculate_sleep_time_end.R:131`）是正确的。参照实现在这一行有误。**

### 争议是什么

参照实现（`calculate_sleep_time_vars.R` 第 49 行）：

```r
self_diffcalc_sleeponset = lubridate::minutes(duration_totalmin_sol_estimate_am_mincalc)
                           + time_sleep_am_hhmm_ampm
```

即 **sleeponset = time_sleep + 自报SOL**。

splsleep 某次改动把它改成了直接取 `time_sleep_corrected`，注释理由是
`"should not be added here or SOL gets double-counted"`。**这次改动此前没有任何文档记录**，
是本轮审计对照截图才发现的。

### 判断依据

**依据一：`SCHEMA.md:13` 的定义**

```
| `time_sleep_hhmm` | `time_sleep_am_hhmm` | character | Sleep-onset HH:MM |
```

`time_sleep` 被定义为 **Sleep-onset（入睡时刻）**，不是「上床准备睡」。

**依据二：参照实现自身存在内部矛盾**

同一份参照实现，第 47 行：

```r
self_diffcalc_sol_minutes = difftime(time_sleep_am, time_bed_am)   # SOL = 睡着 − 上床
```

这一行把 `time_sleep − time_bed` 当作 SOL，**说明它也认为 `time_sleep` 是入睡时刻**。
但第 49 行又给 `time_sleep` 加了一次自报 SOL。

**同一段延迟被计入两次**：一次隐含在 `time_sleep` 的位置里（它本就在 `time_bed` 之后 SOL 那么久），
一次显式加上去。第 47 行与第 49 行对 `time_sleep` 的假设不一致。

**依据三：加 SOL 后的量没有物理对应**

`time_sleep + 自报SOL` = 「睡着之后又过了约 29 分钟」的那个时刻。
日记里不存在这个事件。

### 数值影响

若改为加 SOL：sleeponset 后移 → `sleepperiod = awake − sleeponset` 变短 → **TST 变短同样多**。

按真实数据 Mean SOL = 28.8 min 估算：

| | Mean TST |
|---|---|
| 当前（不加 SOL） | **7.71 h** |
| 若加 SOL | 约 7.23 h |

**差约 29 分钟，系统性、方向单一。** 这个偏移会直接进入论文的主要结局指标。

### 语义已确认

`time_sleep_am` 问的是**「你几点睡着的」**——即入睡时刻本身。这一点由研究者直接确认，
不是从 SCHEMA.md 推断的。

因此：

- `sleeponset = time_sleep_corrected`，**不加自报 SOL**（加了就是把同一段延迟计两次）
- `self_diffcalc_sol_minutes = time_sleep - time_bed` 是正确的 SOL 计算
- `SCHEMA.md:13` 的 "Sleep-onset HH:MM" 定义无需修改
- 参照实现第 49 行的 `+ SOL` 是错的；splsleep 当前实现是对的

**本条已结案，无外部依赖。** `tst_minutes` 可按 primary outcome 正常交付。

## 二、连带发现：`sleepperiod` 与 `trysleep` 按构造相同

### 事实

决定不加 SOL 之后，两个量在代码层面完全等价：

```r
sleeponset  = time_sleep_corrected                            # 131 行
sleepperiod = time_awake_corrected − sleeponset               # 167 行
            = time_awake_corrected − time_sleep_corrected
trysleep    = time_awake_corrected − time_sleep_corrected     # 137 行
```

**不是数值接近，是同一个表达式。** 参照实现里两者不同，正因为它的 sleeponset 加了 SOL。

验证：

```r
d <- readRDS("output/corrected_ema_data.rds")
all.equal(d$self_diffcalc_sleepperiod_minutes, d$self_diffcalc_totaltrysleep_minutes)
```

### 曾考虑并否决的做法

**否决：为了让两列不重复，而给 sleeponset 加回 SOL。**

否决理由：**这是拿算法迁就列表。** 列重复是呈现层的问题，
加 SOL 会改变一个物理量的定义并使 TST 系统性偏移约 29 分钟。
用一个会影响主要结局的算法改动，去解决一个「表里有两列一样」的整洁性问题，
代价与收益完全不成比例。

**这条记下来，是因为它看起来很有诱惑力，且理由听上去合理（"避免冗余"）。**

### 采纳的做法

**Dataset A 只保留 `sleepperiod_minutes`，删去 `trysleep_minutes`。**

保留 `sleepperiod_minutes` 而非 `trysleep_minutes` 的理由：

1. 它是 TST 公式的直接输入（192 行）
2. 它是决策 B2 选定的「TST 上界」
3. 名字更贴近它在本数据集中的实际含义

### 应写入 Methods 的一句话

> 本日记未采集夜间中途醒来的时刻，因此「睡眠期」与「尝试入睡期」在本数据集中不可区分，
> 二者按构造相同。

**这是数据设计的事实，不是缺陷，应当明写而非掩盖。**

## 六、真实数据实测：两个 WASO 的关系（S1 的后续）

`waso_computed_minutes`（= `awake_getup_diff_h × 60`）与 `waso_selfreport_minutes`
在 13,990 行中有 **1,723 行两者皆非 NA**。实测结果：

| | computed | selfreport |
|---|---|---|
| Min | −716 | 0 |
| Q1 | 4 | 5 |
| **中位数** | **10** | **10** |
| 均值 | 18.2 | 15.2 |
| **Q3** | **20** | **20** |
| Max | 384 | 210 |

差值（computed − selfreport）：**中位数 0**，Q1 −10，Q3 +10，均值 +2.96。
差值绝对值分位数：50% = 10、75% = 25、90% = 45、95% = 74、99% = 168 分钟。

### 结论一：边际分布高度一致，但逐行不相关

**相关系数 r = 0.013。**

即：总体上两列描述的是同一个量级的东西（中位数、Q3 完全相同），
但**具体到某一晚，自报值不追踪计算值**。

两种解读并存且无法从数据本身区分：

1. **实质发现** —— 人对夜间清醒时长的感知在单夜层面不准，群体分布却是对的。
   对 discrepancy 研究而言这本身即为结论
2. **测量假象** —— 自报值重度取整（Q1=5、中位=10、Q3=20，全是整五整十），
   取整会显著衰减相关系数

**无论哪种解读，结论一致：两列不可互相替代，分析时必须当两个变量处理。**
已写入字典 `waso_computed_minutes` 与 `waso_selfreport_minutes` 两行的 description。

### 结论二：负值不构成缺陷，无需加守卫

`computed` 最小值 −716 分钟（起床早于醒来，物理不可能）。查证：

```
负值条数: 1 / 非 NA 2848
pid 8018, day 5, row 8502
  time_awake_corrected  2021-07-17 12:13:00
  time_getup_corrected  2021-07-17 00:17:00
  data_category = error   has_correction = both
```

**唯一一条，且已被管线标为 `error`。** 对均值的影响约 0.25 分钟。

**决定：不加下界守卫。** 加了等于在已有的 `data_category` 分类机制之上打补丁，
制造第二套互相不知情的过滤逻辑。分析者按 `data_category` 筛选即可排除。

### 方法教训（记下来因为我犯了两次）

本节两个结论都推翻了我先前基于**手挑 3 行**提出的告警：

- 先说 computed 比 selfreport 大「53 倍 / 6 倍 / 2.5 倍」——
  那是分母为个位数时的比值假象。看分位数，中位数差值正好是 0
- 再说负值可能是系统性 AM/PM 问题 —— 实际 1/2848，且已被标记

**从 13,990 行里挑 3 行看，得不出任何分布性结论。**
下次先跑 `summary()` 和 `quantile()`，再决定要不要提告警。

## 七、算法修正与人工修正的交互问题（由 §六 的一条负值查出）

§六 那条 `waso_computed_minutes = −716` 追下去,牵出两个与 WASO 无关、
但影响面更大的问题。**排查路径值得留档:一条极端值 → `correction_type` →
规则源码 → 三条同类记录逐条复盘。**

### 触发点

`row_id 8502`(pid 8018)最终 `time_awake_corrected = 12:13` 晚于
`time_getup_corrected = 00:17`,时序倒挂 11.9 小时。

`correction_type = getup_reduce_12h_loop`。但那个循环(`normalize_sleep_time_sequence.R:134`)
的退出条件是 `diff < 12`,**数学上不可能产出 −11.9 的结果** ——
要落到 −11.9,上一轮 diff 必须是 +0.07,而 0.07 < 12 早该退出。
说明中间有另一只手动过。`manually_corrected = TRUE`。

### 复盘

原始输入:

```
time_awake_am_hhmm  12:13   ampm AM   →  00:13
time_getup_am_hhmm  12:17   ampm PM   →  12:17
gap = 12.07h ≥ 12  →  规则 4.1 触发  →  getup −12h  →  00:17
```

随后人工把 `awake` 从 00:13 改成 12:13,**但保留了算法已经减过 12h 的 getup**。
那次减法的前提(awake = 00:13)已不成立,值却留下了。

**人工的判断是对的,算法是错的。** 放进完整时序看:

| 读法 | bed | sleep | awake | getup | 自洽 |
|---|---|---|---|---|---|
| 算法(改 getup) | 04:27 | 04:27 | **00:13** | 00:17 | awake 早于 bed ❌ |
| 人工(改 awake) | 04:27 | 04:27 | **12:13** | **12:17** | 睡 7.77h,起床晚 4 分钟 ✅ |

AM/PM 错的是 `awake`,不是 `getup`。

### 问题一：规则 4.1 / 4.2 会猜错「哪个时间戳的 AM/PM 错了」

规则注释写死了假设:

> *"the user likely recorded **getup** with the wrong AM/PM"*（4.1）
> *"the user likely recorded **sleep** with the wrong AM/PM"*（4.2）

**它只看一对时间戳,不拿另外两个当锚点交叉验证。**
4.1 若看一眼 `bed = 04:27`,就能排除「awake = 00:13」这个读法。

全量筛查(`manually_corrected & corrected & correction_type 含 12h_loop`)共 3 条:

| row_id | 算法怪谁 | 实际错谁 | 人工是否改全 | 最终 |
|---|---|---|---|---|
| 8502 | getup | **awake** | ❌ 只改了 awake | `error` |
| 8827 | sleep | 原始值即垃圾(`awake = "0"`) | — | `error` |
| 12078 | sleep | **bed** | ✅ 同时改了 bed 与 sleep | `clean` |

**3 条里人工推翻了算法 2 条,两次人都是对的。** 不是随机噪声,是规则的系统性盲点。

### 问题二：`correction_type` 被人工覆盖后不失效

`row_id 12078`:

| | 原始 | 算法 | 最终 |
|---|---|---|---|
| bed | 12-26 16:00 | 16:00 | **12-27 04:00** |
| sleep | 12-27 04:30 | **12-26 16:30** | 12-27 04:30 |

算法把 `sleep` 减了 12h;人工把 sleep 改了回去,转而给 `bed` 加 12h。
**那次算法修正已被完全撤销,数据里没有它的痕迹,
`correction_type` 却至今写着 `sleep_reduce_12h_loop`。**

**这条直接打在 M6 上。** 0809 决定把 `correction_type` 放进 Dataset B,
理由是让 B 能自足回答「用什么规则改的」——
**对 16 条 `has_correction = "both"` 的记录,它给出的答案是错的。**

### 已确认不是问题的部分

- **唯一真正没修好的是 8502**,且带 `error_type = order_error`,不会静默进入分析。
  它的正确值可推:`getup = 12:17`
- **12078 那条 `clean` 是对的**,人工改全了。先前担心的「同类交互落在
  不亮红灯的地方」在本数据集中未发生
- 8827 是原始输入垃圾(`time_awake_am_hhmm = "0"`),标 `error` 是正确处理

### 修正问责:错的不是审核员,是执行顺序

`manual_error_corrections.csv` 第 69 行(该文件已 gitignore):

```
problem_humanidentified:
  "Awake is recorded as 12:13 AM but getup is 12:17 PM;
   awake likely has AM/PM error and should be noon, four minutes before getup."
column_to_correct    time_awake_corrected
correct_value        Same day 12:13:00 PM
column_to_correct_2  (空)
```

同一行的快照字段显示 `time_getup_corrected = 7/17/21 12:17`、`corrected = FALSE`。

**审核员看到的是归一化之前的状态 —— 那时 getup 还是好的 12:17,确实只需要改 awake。
他的诊断完整且正确,连「比 getup 早四分钟」都写了。**

真正的问题是执行顺序:**算法归一化先跑,把 getup 打成 00:17;人工修正后应用,只改 awake。**
人工修正所基于的前置状态,在它被应用时已经不存在了。

**这条要记牢:不要把它归因为「审核员漏改了一列」。**
那样会导向错误的补救方向(加强人工审核培训),
而真正该修的是管线的执行顺序或重算机制。

> **2026-08-09 决定:不实施。** 研究者原则:管线目前能跑、数字正常、即将交付,

> 那是我默认了它迟早要做,而这是我的假设,不是需求。
> **发现一个缺陷不等于该修它。**

### 为什么不能顺手改

4.1 / 4.2 是整条管线最上游的时间戳归一化。它的输出喂给
时序分类 → 错误标记 → 人工审核队列 → 所有睡眠指标。
**改它等于改动全部下游数字**,包括论文的主要结局指标。

### 关键资产:我们已经有一个带标注的验证集

`manual_error_corrections.csv` 有 **75 行人工裁定过的记录**,每行都带
`problem_humanidentified`(人判断错在哪)与 `correct_value`(正确值是什么)。

**这不是待办事项,这是 ground truth。**

所以 ③ 不该是「凭第一性原理设计一条更聪明的规则然后祈祷」,
而是**可测量的**:新规则在这 75 条上能自动答对多少?现行规则答对多少?

### 设计方向

不再硬编码「错的是 getup」(4.1)/「错的是 sleep」(4.2),改为**枚举 + 打分**:

1. 对 4 个时间戳各自考虑 {不动, −12h, +12h},限制最多 2 个同时位移
2. 每个候选解按现有阈值打分 —— **复用 `error_unusual_sleep_time_corrections.R`
   里已有的常数,不要新发明**:
   - 硬约束:`bed ≤ sleep ≤ awake ≤ getup`
   - SOL = `sleep − bed` ∈ [0, 3h](现有 `bed_sleep_suspicious` 阈值)
   - 睡眠跨度 = `awake − sleep` ∈ [3, 15h](现有 `sleep_awake_suspicious`)
   - 醒后在床 = `getup − awake` ∈ [0, 3h](现有 `awake_getup_suspicious`)
   - 总跨度 `bed → getup` < 24h
3. 取分最高者;平手时取位移数最少者
4. **若最优解不唯一,或全部候选都过不了硬约束 → 不修,直接送人工队列。**
   这一条是重点:现行规则的毛病正是它在信息不足时也要强行给个答案

对照本轮 3 条:8502 的正解(awake +12h)会因 `bed = 04:27` 而把竞争者排除;
12078 的正解(bed +12h)同理。**两条人工推翻算法的案例,新方案都应自动答对
—— 这正是回测要验证的,不是可以预先断言的。**

### 落地约束(缺一不可)

1. **新写 `resolve_ampm_ambiguity()`,不要原地改 4.1 / 4.2。** 旧路径保持默认
2. **config 开关切换新旧**,默认关
3. **回归夹具**:把 8502 / 8827 / 12078 连同期望答案固化成测试
4. **75 条回测**,报告新旧规则各自的自动答对率
5. **全量快照对比**:逐行 diff,所有发生变化的行导出成复查 CSV
6. **验收标准必须在跑之前定死**:
   - 新规则在 75 条标注集上不得低于现行规则
   - 任何当前为 `clean` 的行若被改变,逐条人工批准,不批准就不合入

### 为什么最终否决

收益是**降低未来数据的人工审核量**(不是「修好 3 条记录」——那 3 条已由 ② 解决)。
代价是全部下游数字要重新验证,包括论文主要结局指标。

**在「能跑、数字正常、即将交付」的状态下,这笔交易不划算。**
影响面 3 条记录,其中 2 条已被正确标记、1 条(12078)人工已改对。

### Part 1：算式契约（失败即 FAIL）

## 十三、Phase 1 交付门（v1.4.0 收口）

### 1. affect 层决策：`reserved`，而不是 `dropped`

`column_dictionary.csv` 追加 4 个 `status = reserved` 行：

`pos_affect` / `neg_affect` / `stress_today_pm` / `copestress_today_pm`。

语义：**在则透传、不在则绝不造列**。
`finalize_columns()` 的 4a 段用 `.AFFECT_PATTERN` 正则识别这四列及任意
`*_affect_*` / `*_mood_*` / `*_stress_*` 形态，`cbind` 原样透传。
真实数据（13990 行）不含这些列 → A 仍 36 列，无占位伪造。

> 教训：曾把 `data[affect_cols, , drop=FALSE]` 写成「选行」，报
> "differing number of rows: 3, 4"；应为 `data[, affect_cols, drop=FALSE]`。

### 2. 导出门（export guard）：负数分钟不得出现在可分析行

对 14 个带符号分钟指标，凡是
`record_status` ∈ Analysable(非 `error`、非 `not_reported`) 的行出现负值，
`finalize_columns()` 直接 `stop()`。

**语义修正（由真实数据抓到）：** 第一次实跑
`sleepperiod_minutes` 4 个负值 = 3 `error` + 1 `skipped_na`（row 8566，
pid 6985，`self_diffcalc_sleepperiod_minutes = -10`）。
`not_reported`/`skipped_na` 是整夜缺失，其碎片是算术噪声，不是信号。
故 guard 排除 `error` **和** `not_reported`，与分析师过滤同步。
用户指示「跑完」→ 语义修正后重跑成功：A 13990×36，B 13990×15，full 13990×134。

### 3. Step 10 硬失败

`R/pipeline.R` 删掉 `tryCatch`。字典漂移时 `finalize_columns()` 失败即
**整个 run 失败**（绿码带上错误走的做法已废除）。
