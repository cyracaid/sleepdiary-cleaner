## 三、产出

### 3.1 `R/sleep_diary.R` — S3 类地基

对象结构：`data`（工作数据）+ `step`（本步溯源）+ `history`（步骤链）+ `cfg`。

| 函数 | 作用 |
|---|---|
| `new_sleep_diary()` | 构造器，校验 data 是 data.frame、step_id/label 是单个字符串 |
| `validate_sleep_diary()` | 结构不变量校验，边界处大声失败而不是三步之后莫名出错 |
| `as_sleep_diary()` / `is_sleep_diary()` | 强制转换（幂等）/ 类型判断 |
| `print()` | 一行状态：第几步、多少行列、耗时、新增列、链长 |
| `summary()` | 每步一行（进/出行数、新增列数、毫秒），ledger 有数据时自动 join 上 flag 计数 |
| `plot()` | ggplot2 在就用，不在就退回 base barplot，绝不因 Suggests 缺失而报错 |
| `as.data.frame()` / `dim()` | 向后兼容逃生口 —— v1.2 的代码拿 `as.data.frame(x)` 就能照旧跑 |

**注意**：`nrow` 在 base R 里不是泛型，它经由 `dim()` 派发，所以写的是 `dim.sleep_diary` 而非 `nrow.sleep_diary`。

### 3.2 `R/steps.R` — 6 个步骤适配器

包住 v1.2.0 脚本，**清洗逻辑一行未改**：

| 适配器 | 包住的脚本 |
|---|---|
| `step_process_timestamps()` | `process_timestamp_emadatarelease_cyra.R` |
| `step_process_intervals()` | `process_interval.R` |
| `step_normalize_sequence()` | `normalize_sleep_time_sequence.R` |
| `step_apply_corrections()` | `error_unusual_sleep_time_corrections.R` |
| `step_apply_duration_corrections()` | 三个 `apply_*.R`，保持原有调用顺序 |
| `step_compute_metrics()` | `calculate_sleep_time_end.R` |

所有适配器走同一个咽喉 `.run_step()`：计时 → 调用原脚本 → 校验返回值是 data.frame → 调 `log_step()`（参数与顺序与 v1.2.0 完全一致，ledger 与 Figure 12 不受影响）→ 装箱。

脚本用 `sys.source()` 载入私有环境（`parent = globalenv()`），避免污染全局环境，同时让脚本仍能取到 `pipeline_config` / `cfg_get`。

`assert_contract_columns()` 把 Step 7 的四个公共契约列（`sleep_efficiency_pct` / `sol_h` / `waso_h` / `sleep_duration_h`）从"假设"变成"断言"。

### 3.3 `R/pipeline_chain.R` — `run_cleaning_chain()`

把 6 步串成一条链，返回 `sleep_diary`。

**刻意不纳入链条的步骤**：1（读数据）、1.5（字段误填检查）、5（生成复核文件）、5.75（二次复核共识）、8（自动检测）、8.5（跨被试检查）、9（出图）。这些写文件或往全局环境塞对象，硬塞进链条是**改行为**而非**换形状**。它们留在 `run_pipeline()` 里，等 snapshot 测试覆盖后再动。

### 3.4 `tests/testthat/test-sleep-diary.R` — 11 组测试

全部用合成数据，CI 上无需真实数据集、无需任何 Suggests 包即可跑：构造 / 拒绝畸形输入 / 校验器抓结构损坏 / 幂等转换 / `as.data.frame` 原样返回 / dim-nrow-ncol 派发 / print 输出 / summary 制表 / 契约列断言（正反两面）/ 步骤拒绝非 data.frame 返回值 / 步骤记录溯源并增长 history。

## 四、关键设计取舍

**`run_pipeline()` 本轮零改动。** 它仍走 v1.2.0 的原路径。理由：在 correction engine 还没有 snapshot 测试保护时，把生产路径切到新链条，一旦结果有差异将无从判断是重构引入的还是本来就不同。切换动作留到 P1-2 的 snapshot 测试就位之后 —— 那时可以逐行比对新旧 `corrected_ema_data`，差异为零才切。

这也是"包装层优先"策略的核心：**先有契约和测试，再动内脏。**

## 五、已知限制

1. **本轮代码未经运行验证。** 沙箱无 R 环境（无 root，apt 被锁），只做了静态检查：非 ASCII 0 处、括号配平通过、NAMESPACE 与函数定义一致。实际 `load_all()` / `test()` 需在本机跑。
2. 适配器每次调用都会重新 `sys.source()` 一遍脚本（2077 行的 correction engine 也不例外）。当前规模下可接受，若成为瓶颈再加环境缓存。
3. `summary()` 的 ledger join 依赖 `log_step()` 已被调用过；独立使用类而不跑管线时该列为空，属预期。
