## 一、SOL/WASO 静默误改补丁（Part A4）

### 背景

上一轮合成 benchmark（n=400/类）测出：`field_misentry_sol`/`field_misentry_waso`（时钟时间误填进 duration 字段）静默误改率 95.8%/96.0%，且已定位根因——`sol_duration_for_review_status`/`waso_duration_for_metrics_status`（`calculate_sleep_time_end.R` 第 130-181 行）只检查解析值是否**超过**睡眠窗口，从不检查是否**过小**，而 `process_interval.R` 的 MM:SS 重解释启发式恰好把这类误填变成小的、看似合理的数字，正好从这个单向检查的盲区溜过去。

另一个 AI review 这份报告后提出了一版补丁，但**原样照抄会直接崩掉**：

1. **目标文件错了。** 原方案把代码插进 `calculate_sleep_time_end.R`（Step 7），引用 `needs_review_flag`。实测 `grep -rn "needs_review_flag\s*<-\|needs_review_flag\s*="` 确认这个变量是在 `checkforerrors_processing.R`（Step 8，晚于 Step 7）才创建的——Step 7 里根本不存在这个变量，插进去会报 `object 'needs_review_flag' not found`。
2. **匹配模式不完整。** 原方案只匹配文本 `"MM:SS"`。实测 400 条 benchmark 数据发现有 7 例走的是另一条日志文本（`"dd:00 -> 00:dd"`），只用 `"MM:SS"` 会漏掉这 7 例。

### 实际改动

在 `checkforerrors_processing.R` 里新增 "PART A4" 代码块，插在既有 Part A3 之后、"PART B: Import temporal error/unusual flags..." 之前，沿用文件本身的 base-R 风格（不用 dplyr）：

```r
risky_reinterpretation_pattern <- "MM:SS|dd:00"
sol_waso_note_cols <- c(
  sol  = "duration_totalmin_sol_estimate_am_correctionsmade",
  waso = "duration_totalmin_waso_estimate_am_correctionsmade"
)
for (label in names(sol_waso_note_cols)) {
  col_name <- sol_waso_note_cols[[label]]
  if (col_name %in% names(data)) {
    risky <- !is.na(data[[col_name]]) & grepl(risky_reinterpretation_pattern, data[[col_name]])
    flag_idx <- which(risky & !data$manually_corrected)
    for (i in flag_idx) {
      data$needs_review_flag[i] <- TRUE
      desc <- paste0("[DurationReinterp] ", label, ": ", data[[col_name]][i])
      data$auto_error_desc[i] <- if (is.na(data$auto_error_desc[i])) desc
                                  else paste(data$auto_error_desc[i], desc, sep = "; ")
    }
  }
}
```

补丁自带的注释里写明了一个**已知盲区**：约 3.5%（14/400）的 `field_misentry_sol` 案例形如 "01:07"–"01:59"，解析后是普通合法的 HH:MM 值，`_correctionsmade` 完全不留文本痕迹——这类案例这个补丁结构性抓不到，需要语义而非文本匹配的方法才能覆盖。这条注释是**打补丁之前**写的预判，不是事后找补。

### 验证（打补丁前后各跑一次，对照）

| | 补丁前 | 补丁后 |
|---|---|---|
| FCR n=10,000 全干净数据，新规则误报数 | — | **0/10,000** |

## 四、通道B冗余验证（真实数据 n=13,990，今天新做的核心工作）

对照 `validation-design.md` §1——文档原话说这是第一梯队里"最大的单项收益"，因为不需要任何合成注入、不需要人工标注，直接在真实数据上验证。

### 逻辑

原始日记里同时存在两个互相独立的 SOL 测量：自报时长（`duration_totalmin_sol_estimate_am`）和时间戳推算（`time_sleep − time_bed`）。**前提是 Step 4（`normalize_sleep_time_sequence.R`）的纠正逻辑完全不看 duration 列**——先用 `grep -n "duration_vars"` 确认了这一点：`duration_vars` 在第 46-52 行声明、筛选后就再没被引用过。这意味着自报 SOL 是一条 Step 4 纠正算法看不到的独立判据，可以在真实数据上直接测"纠正对不对"，不构成循环论证。**这条验证的适用范围严格限定在 Step 4 输出**（`ema_data_release_timecalc`，`R/pipeline.R` 里 `step_normalize_sequence()` 跑完之后立刻捕获的那个快照，早于 Step 5/6 碰任何东西）——晚于 Step 4 的所有步骤都会读 duration 列，重复做这个验证就会循环论证。

### 拿真实数据踩的一个坑

真实主数据文件 `deidentified_intervalvars_forCD_111325.rds`（13,990 行，这才是 README 里 `verification/real_n13990/` 对应的那份数据，`synth_n280` 才是合成 demo）里没有 `StartDate` 列，而 `process_timestamp_emadatarelease_cyra.R` 第 157 行需要用 `substr(StartDate, 1, 10)` 拼出完整 POSIXct。原本以为要用 `sber_ema_anon_20260227.csv`（14,687,417 字节的原始 Qualtrics 导出）里的 `StartDate` 补上，但这份 CSV 是 14,216 行，跟主数据的 13,990 行对不上，`run_pipeline()` 的 extra file 加载器要求逐行位置严格一致，直接用会报 `Row mismatch`。

**解决：给每一行填一个统一的占位日期（"2024-01-01"）。** 这样做是安全的——`StartDate` 只用来给同一行的四个时间戳提供日历日期，Channel B 分析只用同一行内部的相对时间差，占位日期对所有相对计算没有影响。跑通之后成功捕获到 `ema_data_release_timecalc`（13,990 行 × 78 列），Step 5 因为一个跟这次分析无关的配置问题（缺 `num_waso_estimate_am`）报错，但这发生在快照捕获**之后**，不影响结果。

### 健全性检查（先过了才敢信后面的结果）

- 未被 Step 4 纠正的行（`correction_type` 为 NA，n=2,751）：纠正前后差值变化精确为 **0.000000**，跟源码里"未触碰的行 `_corrected` 就是原值的拷贝"这句话完全对得上。
- 被纠正但跟 bed/sleep 无关的行（`awake_getup_swap_3h`/`getup_reduce_12h_loop`，n=11）：这个指标上也测出精确 0 变化——证明指标本身没在测噪音。
- 99 条被 Step 4 纠正的行里，**全部 99 条**都有可用的自报 SOL 数据，corrected 子集里没有因为缺失值被排除导致的偏差。

## 五、B1 描述性分析（真实数据，`time_sleep` 语义确认）

用户提出：既然通道B验证的前提是"自报SOL和时间戳推算SOL是两条独立测量"，那"这到底是不是冗余"这个问题本身，是不是也该放在通道B里面一起解决？——这正好是 `validation-design.md` §1 坑1 里说的"一石二鸟"：B1（`time_sleep` 问的是"熄灯"还是"睡着"）和通道B的前提是同一件事的两面，而且不需要用户提供任何新数据，直接复用今天上午已经跑出来的真实 n=13,990 checkpoint（`ema_data_release_timecalc_real_n13990.rds`）即可。

### 方法

对比两个假说：
- **入睡时刻假说**：`time_sleep − time_bed`（原始，未纠正）应该 ≈ 自报SOL（对角线）
- **熄灯时刻假说**：这个差值应该 ≈ 0，跟自报SOL无关（水平线）

**刻意只用 Step 4 没有纠正过的 2,735 条记录**（`correction_type` 为 NA），且用**原始未纠正**时间戳——不用全量 13,990 条。原因：全量原始数据里混着 Step 4 本来就是为了修的 AM/PM 翻转/顺序错位痕迹（原始gap里有一簇恰好卡在 ~750 分钟≈12.5 小时的异常值，是时钟误填的痕迹，不是真实作答），拿这些去测"参与者到底怎么理解这个问题"会把两个不同性质的问题混在一起。2,735 条里进一步排除了 55 条 gap 为负数（sleep 早于 bed，两种假说下都不合理）和自报SOL缺失的记录（自报SOL整体缺失率很高：13,990 条里只有 20.4% 非缺失，这是这个EMA题项本身的应答率问题，这次分析处理不了）。

### 结果

- 点对点相关性**弱**：Pearson r=0.13，Spearman ρ=0.15（R²=0.017）
- 差值中位数 `gap − SOL` = 5 分钟（均值 13.8 分钟，被长尾拉高）；59.9% 的记录落在入睡假说预测值 15 分钟以内，91.7% 落在 60 分钟以内
- **按自报SOL分10个bin看中位数gap，从~15分钟涨到~37.5分钟**——这一点已经足够排除"熄灯"假说（那样的话不管SOL多大，中位数gap应该都摁在0附近，但没有）
- 在自报SOL 0–30分钟这段，趋势线跟对角线贴得比较近；但在40–90+分钟这段，趋势线明显低于对角线——自报SOL系统性比时间戳gap长

### 解读

数据**排除了"熄灯"假说**（趋势线明显不是摁在0附近），方向上支持"入睡"假说，但个体层面匹配并不紧密（R²只有0.017），这是一个**总体层面的倾向**，不是精确的逐条对应。高SOL段自报比时间戳推算长，这个模式在睡眠研究文献里本身就有记录（自报入睡潜伏期在长潜伏期时容易系统性高估，相对更客观的测量方式），是一个有文献支持的解释，不需要另外假设 `time_sleep` 问的是别的东西。**这次分析是确认性质，不是打开一个新问题**——研究者已经在 `2026-08-09_work_log.md` 里直接确认过 `time_sleep_am` 问的是"几点睡着"。今天这轮是用真实数据做的独立、数据驱动的交叉验证，不是重新打开这个问题。

**这次分析解决了什么、没解决什么：** 解决了方向性问题（入睡，不是熄灯），用的是真实数据证据而不只是问卷原题措辞。**没有**产出一个可以在个体层面替代自报SOL的精确校正值——R²太低，这个gap不能在单条记录层面当自报SOL的替代品用，只能像通道B主分析那样，做纠正前后的相对配对比较，不能当绝对值用。
