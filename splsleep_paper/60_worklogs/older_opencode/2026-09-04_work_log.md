### Why this section exists

A "590-row" figure for negative Sleep→Awake timestamp gaps circulated across
sessions with no traceable derivation. This section is the full paper trail,
so no future session cites 590, 126, or 134 again — only the number below,
with the script that produces it.

### The chain, and why each earlier number is wrong except the last one

- **590** — could not be reproduced under any AM/PM-mapping × wraparound-logic
  combination tested against `sber_ema_anon_20260227.csv`. The session that
  originally reported it confirmed it was fabricated.

- **126 / 134** — produced by a naive same-session Python reimplementation.
  It used the *correct* AM/PM mapping (l=PM, c=AM — confirmed independently
  via median-TST plausibility, 8.00h vs. 19.83h for the wrong mapping) but a
  plain same-calendar-day hour subtraction. That reimplementation missed two
  business rules that already exist, are already documented, and are already
  verified against an archived export in `R/timestamp_parse.R`:
  1. Evening-variable (bed/sleep) clock time "12:00" marked PM is actually
     midnight, not noon.
  2. Evening-variable clock time > 15:00 belongs to the *previous* calendar
     day (date rollover), so the gap to the next event isn't computed
     same-day.
  Concrete false positive that demonstrates the bug: **PID 6374, day 12** —
  raw sleep time "12:00" coded PM. Naive script: read as noon (12.0h),
  awake = 7.92h, gap = -4.08h → false 3-6h-negative hit. Real rule: "12:00"
  PM for an evening variable = midnight (0h), gap = +7.92h → not a candidate.
  87 of the 126 naive `gap_sleep_awake` hits are this class of false
  positive.

- **46 — locked.** Produced by `validation/derive_timegap_candidates.R`,
  which calls the pipeline's real `process_timestamp()`
  (`R/timestamp_parse.R`) instead of reimplementing the decode. Breakdown:
  `gap_sleep_awake` = 39, `gap_awake_getup` = 6, `gap_bed_sleep` = 1. No
  pid+day_num triggers more than one pair (46 rows = 46 distinct diary-days).

### Second false-positive mechanism (added 2026-09-02, same audit)

The PID 6374 day-12 example above (business rule 1: hour=12 marked PM on an
evening variable is midnight, not noon) is one of two distinct ways the
naive reimplementation manufactured false positives. The other mechanism —
business rule 2, date rollover — is also demonstrated by PID 6374, on a
different pair of days:

**PID 6374, day 4 and day 5 — `gap_bed_sleep`.** Raw: bed = "09:00" coded
PM (→21:00), sleep = "03:00" coded PM (→15:00).
- Naive (same-calendar-day subtraction): gap = 15.00 - 21.00 = **-6.00h** →
  false 3-6h-negative hit (this is the "6374, day 4 / day 5" pair originally
  listed as candidates before real decoding).
- Real (`process_timestamp()`, verified by direct execution): bed's
  clock-time (21:00) is > 15:00, so it is dated to the *previous* calendar
  day (2021-04-23), while sleep's clock-time (15:00) does not cross that
  threshold and stays on the diary date (2021-04-24). Once dated correctly,
  gap = **+18.00h** — nowhere near a 3-6h negative candidate; the naive
  calculation was comparing two clock times that don't actually belong to
  the same day.

Both false-positive mechanisms are the same shape: the naive reimplementation
decoded the raw text literally instead of applying rules this dataset is
already known to need, documented and verified in `R/timestamp_parse.R`
well before this audit. Neither mechanism is specific to PID 6374 — both
rules apply uniformly whenever an evening-variable clock time is exactly
12:00-marked-PM (rule 1) or > 15:00 (rule 2), so any row with either pattern
was at risk of the same false-positive class in the naive count.

### Boundary-sensitivity check (added 2026-09-02, same audit)

Before treating 46 as final, checked whether the two decode-artifact
mechanisms above ever produce a "soft" false positive -- a row that leaves
the 3-6h band but lands in some other suspicious-looking negative range
instead of cleanly going positive -- and whether the count is stable near
the 3h/6h edges. Compared naive vs. real gap for every row, all three pairs:

- **No hidden reversals.** All rows removed by the two decode fixes land
  solidly positive: `gap_bed_sleep`'s 2 removed rows both land at exactly
  +18.00h; `gap_sleep_awake`'s 87 removed rows land between +6.00h and
  +18.50h (median +7.5h). None land in a different negative band. The
  46-row set is not hiding a differently-shaped problem.

- **Real edge sensitivity.** 6 of the 39 `gap_sleep_awake` rows sit within
  0.25h of the 3h or 6h boundary (e.g. a row at -3.1h). This isn't a bug --
  the 3-6h cut is a threshold we chose, not a natural gap in the data, so a
  handful of rows are genuinely borderline. Roughly 40 of the 46 rows are
  threshold-stable; ~6 are boundary-sensitive and worth flagging for extra
  scrutiny in the 2-annotator review rather than treated as equally solid.

- **One false negative caught, not just false positives removed.** PID
  2854, day 7 (`gap_awake_getup`): the naive Python reimplementation
  produced `NA` for this row (its cruder hh:mm cleanup didn't handle
  whatever non-standard format this row has), so it never had a chance to
  be flagged either way. The real `process_timestamp()` -- which has more
  complete string-cleanup logic -- parses it correctly and finds a genuine
  -3.33h candidate. This is why `gap_awake_getup` is 6 in the locked count
  but only 5 in the naive one: not an artifact, a real row the naive script
  silently dropped.

### Bayesian + 2-annotator disambiguation script for the 46 locked time-gap candidates (added 2026-09-02, same audit)

Follow-up to the direct question "你做了吗" (did you build the

**Built two scripts, both verified against real data before delivery:**

- `validation/disambiguate_timegap_candidates.R` -- for each of the 46
  locked candidates (re-derives nothing; consumes `derive_timegap_
  candidates.R`'s output as-is), computes a personal-baseline context
  (median/MAD of the participant's OTHER valid days for the same field
  pair, reusing `cross_participant_global_check.R`'s exact approach) and a
  two-hypothesis Bayesian decision-support score: prior = `error_catalog.
  yaml`'s own real-audit anchor (0.6%), likelihood ratio from
  `n_recurring` (how many of the participant's other days show a
  similarly-large negative gap for the same pair) using fixed round-number
  LR values (1/12 isolated, 1 uninformative, 12 recurring). Outputs TWO
  separate, identical worksheets (`disambiguation_worksheet_cyra.csv`,
  `disambiguation_worksheet_maia.csv`) with blank `judgment`/`notes`
  columns, sorted so the least-informative-score rows surface first.
  Deliberately two files, not one shared file, to avoid the exact failure
  mode documented in `development-evidence-audit.md`:
  `manual_error_corrections.csv`'s `agreement_cd_mtb` column turned out to
  record one shared/collaborative pass, not two independent codings,
  making Cohen's kappa retroactively uncomputable.

- `validation/compute_disambiguation_agreement.R` -- reads the two
  completed worksheets back (merge on pid+day_num+field_pair, not row
  order), computes raw agreement %, Cohen's kappa (hand-computed 3x3
  confusion matrix -- no irr/psych dependency), and writes out the
  disagreement rows for actual discussion. Treats blank judgments as
  "incomplete" (excluded, reported separately, never silently dropped) and
  anything outside {error, behavior, unsure} as "invalid_label" (flagged,
  not silently coerced).

**Bug found and fixed before shipping (caught by hand-checking the output
against the script's own documented intent, not just a parse check):** the
first draft's posterior formula multiplied prior odds by the LR
(`posterior_odds <- prior_odds * lr`), but `lr` is LR(behavior:error) --
incorporating it into odds-of-error requires *dividing*, not multiplying.
The bug silently inverted the signal: isolated rows (meant to "lean
error") were coming out with LOWER posterior_p_error than recurring rows
(meant to "lean behavior") -- backwards from the script's own stated
design. Caught by computing the real output on the actual 46 rows and
checking specific known rows (e.g. PID 6259's isolated `gap_bed_sleep`
candidate) against the documented direction before ever handing this to a
human reviewer. Fixed to `posterior_odds <- prior_odds / lr`; re-ran and
confirmed the fix: isolated rows now correctly score 0.068 (highest,
leans error), recurring rows now correctly score 0.001 (lowest, leans
behavior), n_recurring==1 or <3-other-days rows stay at the ~0.006 prior
(uninformative) either way.

### v7 posterior — stress-tested, one structural limitation found and surfaced (added 2026-09-02, same audit)

Asked to stress-test/validate the v7 Bayesian posterior before treating it as
settled, and record the results here. Four tests run against the real staged
data, plus one further calculation prompted by test 4's result that turned
out to be the most important finding of the five.

**Test 1 — leave-one-out calibration on the 13 known gap_sleep_awake cases
(checking for circularity).** For each of the 13 known cases in turn,
recomputed `BASE_RATE_PRIOR_ODDS` and `LR_SOL_GOOD`/`LR_SOL_POOR` with that
one case excluded, then scored the held-out case with the refit numbers.
All 11 "good"-fit cases correctly land at 99.1%. Both "poor"-fit cases (PID
6805 day 7, PID 11554 day 15 — already flagged in the v5→v6 note as
genuinely messier real cases) still land at 72.0%, correctly favoring error
even in the worst-calibrated fold. No false-negative behavior observed on
the known sample; the pipeline isn't just recovering numbers it was fit on.

**Test 2 — independence check between the two LRs used in
_combined.** The v7 header already flags that multiplying LR_SOL and
LR_participant_prior assumes independence (naive Bayes), and that this could
be wrong if a participant's systematic AM/PM habit drives both signals from
one underlying cause. Cross-tabulated `sol_crosscheck_fit` ×
`participant_prior_signal` on the actual 26 needs-review rows:
(good,error_only)=10, (good,none)=10, (good,behavior_only)=1, (good,mixed)=1,
(poor,error_only)=2, (poor,none)=2. P(error_only_history | good fit) =
10/22 = 0.45 vs P(error_only_history | poor fit) = 2/4 = 0.50 — close enough
that the two signals don't look strongly coupled on this set. Reassuring,
not conclusive — n=26 is small and this doesn't rule out coupling the data
just can't see yet.

**Test 3 — prior sensitivity.** Recomputed the base-rate posterior under
three different priors on the same 13/13 all-error observation: Jeffreys
Beta(0.5,0.5) → mean 3.6% behavior-rate, 95% CI (0%, 17.3%), odds 27.0
(what v7 uses); flat Uniform Beta(1,1) → mean 6.7%, CI (0.2%, 23.2%), odds
14.0; a deliberately skeptical Beta(1,4) → mean 5.6%, CI (0.2%, 19.5%), odds
17.0. Implied P(error) ranges only 93.3%–96.4% across all three — the
qualitative conclusion ("very likely error") doesn't depend on which
reasonable prior is picked.

**Test 4 — LR sensitivity to the reference class used for
P(sol_fit=good | behavior).** v7 approximated this from the narrow 21-row
`bed_sleep_suspicious`/`multiple_suspicious` subset of
manual_unusual_corrections.csv (4/21 = 0.190). Recomputed using the full
37-row unusual file instead: 14/37 = 0.378 — nearly double. That would move
LR_SOL_GOOD from 4.45 to ≈2.24 and LR_SOL_POOR from 0.19 to ≈0.248, and
would move the posteriors from 99.2%/83.7% (good/poor) to about 98.4%/87.0%.
Moderate sensitivity in the exact numbers, but "very likely error across the
board" holds under either reference class.

**Test 5 — the important one, found while checking test 4's numbers: the
posterior as designed cannot ever call a row "likely behavior."** Worked out
what LR_SOL_POOR would have to be to pull `posterior_p_error_solonly` below
50%, given `BASE_RATE_PRIOR_ODDS = 27.0`: solving odds × LR < 1 needs
LR < 1/27 ≈ 0.037. The actual LR_SOL_POOR in use is 0.19 — roughly 5x too
high to get there, and even the more conservative test-4 estimate (≈0.248)
is further still. In plain terms: the 27:1 base-rate prior is strong enough
that no sol_crosscheck result, however poor, can drag a gap_sleep_awake
candidate's posterior under 50% under this design. The posterior can weaken
its confidence (99% down to ~84-87%) but structurally cannot flip a verdict.
This is a real limitation of using a base rate this lopsided (13/13 known
cases) as the dominant term — it means _solonly and _combined should be read
as "how much does this row's evidence still support error," never as
"could this row be behavior instead." No behavior case has been confirmed
for this candidate type yet, so this hasn't caused a wrong call in practice,
but the design should not be trusted to catch one if it existed. Recorded
here rather than smoothed over, per this project's standing practice of
reporting negative/limiting findings alongside positive ones.

**Net:** the v7 posterior calibrates well (test 1), its two LRs don't look
strongly coupled on the available data (test 2), its qualitative conclusion
is robust to prior choice (test 3) and reasonably robust to reference-class
choice (test 4) — but it has a structural blind spot (test 5): it cannot
detect a true behavior case among gap_sleep_awake candidates even in
principle, because the base rate alone already implies >50% before any
row-level evidence is added. Still informational-only, still no auto-skip of
review — this finding is an argument for keeping it that way, not a reason
to change that. No code changes made this pass; this was a validation-only
exercise. If a routing-tier decision is made later (still open, see v6→v7
note), this limitation should be part of that conversation.

### sol_crosscheck reference class — a closer-matching (but tiny) sample found; it argues for MORE caution, not less (added 2026-09-03)

Asked whether the 26 needs-review rows could still be reduced further. Answer
is basically no — everything in the current data has been squeezed already
(see v4→v7 notes above); the one new thing found this pass is a caution, not
a reduction.

`manual_unusual_corrections.csv`'s `unusual_type` column has four values:
`bed_sleep_suspicious` (15), `awake_getup_suspicious` (11),

reference-class estimates: `sleep_awake_suspicious` (5) — the one that

(gap_sleep_awake) exactly, rather than the bed/sleep proxy v7 used because
no exact-match behavior sample existed at the time this was written up.

search, so treat as directional, not a replacement for a properly-coded
version): joined these 5 rows' bed/sleep times against self-reported SOL
(`duration_sol_estimate_am_hhmm`, hand-picked from the raw file's duplicate
per-day rows since the naive join returns multiple records per pid/day_num).
Result: 2 of 5 (PID 8116 day 14, PID 7415 day 11) come back "good fit"
(diff ≤ 30 min) despite being confirmed genuine behavior
("reasonable unusual record... insomnia" in the human note) — 40%, not the
19% v7's proxy class implied, and higher even than stress-test-4's broader
37-row estimate (37.8%).

n=5 is too small to replace v7's LR_SOL_POOR outright, and this wasn't run
through the actual sol_crosscheck_for() ±12h search, so it's not proposed as
a code change here. But directionally it agrees with stress test 4
(2026-09-02): every time the reference class for "what does a genuine
behavior case's sol_crosscheck look like" gets closer to the real target
population, the "good fit" rate among confirmed-behavior cases goes UP, not
down — meaning LR_SOL_POOR = 0.19 (and by extension LR_SOL_GOOD = 4.45) is
probably an optimistic, TOO-discriminating estimate. A real behavior case
turning up "good fit" 40% of the time (rather than 19%) means "good fit"
alone is weaker evidence for error than v7's number suggests.

**What this means in practice: it does not open any new room to skip
review.** It was never used to skip review (context-only, per the standing
design rule), but this finding is a reason to trust that column even less
if anyone were tempted to lean on it informally during review — a "good
fit" row is not obviously safer to rubber-stamp than a "poor fit" one. All
26 needs-review rows stay exactly as before: full review, no shortcuts.
If a properly-coded rebuild of the LR estimates is wanted later, this
5-row class (and a corrected per-day self-report join) is the place to
start, but it should wait for a larger confirmed-behavior sample for this
field_pair before being trusted for anything beyond context.
