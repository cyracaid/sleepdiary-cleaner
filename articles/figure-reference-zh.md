## 1. 如何看图

图保存在 `latest_visualization_<tag>_n<rows>/`（每次运行覆盖——无历史）。
`figure_index.png`
总览所有图；如果有图没能生成，整张图**最顶部**会有一个红色的 “FIGURE(S)
NOT GENERATED THIS RUN”
区块，逐条列出没生成的图和原因。稳定验证产物（snapshot、Bland-Altman
图、阈值验证）单独在 `output/verification/<tag>/`。

**第一次看这些图？** 先看 `figure_index.png` 总览，再按顺序过一遍下面 “5
张必看检查图”——它们合起来就是一次浓缩版的睡眠数据质量
QC。这里出现的每个图号（比如 “F01”、“F09”）都是文件名、图内标题，以及 §4
或 §5
里那张卡片用的同一个编号，可以直接跳过去看完整解释。文件夹的划分（`pipeline_cleaning/`
= 质控/审计图， `research_ready/` =
为论文准备的图）只有在你决定论文放哪张图时才重要——
如果只是检查数据，按图号找就行，不用管文件夹。

**两套图号。** `F01`-`F37`
是管线自己的编号：文件名、图内标题、卡片标题，以及本文所有交叉引用都用它。*论文*编号是另一套，只用于稿件：Methods
图 1–2、Results 图 3–13、补充材料图 S1–S24。§3
索引里”论文图”一列把两套对应起来，每张卡片末尾的图注用的是论文编号，可以直接粘进稿件。

**出版用图（Methods 部分）：**

| 图 | 文件 | 显示什么 |
|----|----|----|
| **图 1 — 管线流程** | `pipeline_cleaning/F01.png` | 垂直流程图：raw → 解析 → 算法修正 → 人工修正 → 最终有效，各阶段计数与 % |
| **图 2 — 修正影响** | `research_ready/F22.png` | A/B delta lollipop（仅修正记录，TST & SOL）+ 一致性散点 + 前后汇总表 |

**5 张必看检查图：**

| 步骤 | 图（卡片） | 应该长这样 | 若不是？ |
|:--:|----|----|----|
| 1 | **F01 管线记录流** (§4) | 流程平缓收窄；Clean 占主导；Error + Unusual 很小（\< 5%） | 0 处有尖峰或 Error/Unusual 占比巨大 → 上游解析/AM-PM 失败 |
| 2 | **F15 逐步标记账本** (§4) | Corrected 柱只在 Step 6.5 出现，之后持平 | Step 6.5 之后再变化 = 不稳定 |
| 3 | **F14 自动检测仪表板** (§4) | 标记计数与 `correction_status_final.csv` 一致 | 不一致 = 错位 |
| 4 | **F23 睡眠变量分布** (§5) | TST 峰值在 6–8 h，SOL 右偏，WASO \< 60，SE \> 85% | SOL 平/双峰 = AM/PM 混淆未修正 |
| 5 | **F06 错误类别分布** (§4) | 多数记录 Clean/Minor；Error+Unusual \< 5% | 偏高 → 审查人工 CSV |

## 2. 输出文件夹里有什么

文件夹名 = `latest_visualization_` + 数据集**标签**（`real`、`synth`
…）+ `_n` + **输入记录数**（例如 `latest_visualization_real_n13990`
表示真实数据、13,990
条记录的一次运行）。每次可视化运行都会**从头重建**，是”最新”而不是”历史”，想保留的东西请在重跑前复制走。标签是
`real` 时里面是由参与者数据生成的图：已被 gitignore，不要提交或外传。

| 项目 | 是什么 | 什么时候看 |
|----|----|----|
| `pipeline_cleaning/` | 21 张诊断图：流水线发现了什么、改了什么（卡片见 §4） | 检查清洗是否正常；补充材料的审计链 |
| `research_ready/` | 16 张面向论文的图：睡眠指标、感知偏差、物质使用（卡片见 §5） | 为 Results 选图 |
| `figure_index.png` | 全部图的总览。顶部红色块列出被跳过的图及原因 | 运行后先看这个 |
| `all_figures_review.pdf` | 每页一张图，按生成顺序，与 PNG 同尺寸 | 快速翻看全部图，或发给研究团队内的合作者 |
| `figures_not_generated.csv` | `file`、`reason`：**没有**生成的图及原因（如”完整数据的标记列不足 2 列”、或缺少某个验证文件）。与红色块同一份清单 | 少了某张 PNG：先看这里，不要先怀疑有 bug |
| `flag_distribution.csv` | 每条日记一行（`pid`、`day_num`、`row_id`），含各类标记数（`timestamp_flags`、`duration_flags`、`amount_flags`、`review_flags`）、`flag_details`、`raw_category`、`final_status`、是否 `manually_corrected`，以及 `data_category_after_corrections`。人工修正过的行只有在 Step 8 检查和 `data_category` 都通过时才是 `CLEAN (Manually Fixed)`；带 Step 8 标记的保留该标记；`data_category` 仍不通过的标为 `STILL FAILS (Manually Corrected)` | 标记类图（F03、F06、F13、F14）背后的表；筛选它找到某根柱子对应的条目 |
| `classification_summary.csv` | 各最终分类（clean / error / unusual …）的数量。仅当本次运行产生了最终分类才写出 | 与 `correction_status_final.csv`（[读懂输出](https://cyracaid.github.io/sleepdiary-cleaner/articles/interpreting-output-zh.md) §4）对照 |
| `RUN_INFO.txt` | 运行时间、数据集标签、记录数、输入文件名、包版本、验证文件位置 | 记录这批图来自哪次运行 |

**同级的 `verification/<tag>_n<rows>/`**（与本文件夹并列，真实数据时在
`output/`
下）在图被重建时**不会被清空**。里面是检验流水线用的证据，不是论文用图：

| 项目 | 是什么 |
|----|----|
| `bland_altman_sol.png`、`bland_altman_waso.png` | Bland-Altman 图：自报与计算的 SOL / WASO 的一致性 |
| `threshold_validation.csv` | 每个标记阈值、测量噪声（`loa_half_width`）、两者之比与评估（如 “CONSERVATIVE”、“SAFE”） |
| `snapshot_*.rds` | 在命名时点保存的数据副本，用于[回归对照](https://cyracaid.github.io/sleepdiary-cleaner/articles/interpreting-output-zh.html#s-6) |
| `PROVENANCE.txt` | 说明某个文件为何存在、何时生成 |

### 3.1 图是怎么编号的

- **只有一套编号：`F01`-`F37`。** 自 1.7.1
  起，文件名、图内标题、卡片标题和本索引里的编号是同一个数。没有缺号，也没有字母后缀：1.6.0
  重新分类时退役的编号已重新分配，而不是留空。
- **按文件夹分族。** `pipeline_cleaning/` 放
  F01-F16（管线图与检测图按生成顺序交错）和
  F17-F21（反序与钟点两类，最后加入）；`research_ready/` 放
  F22-F37。所以在 `pipeline_cleaning/`
  内部，检测图（F06-F14）的编号可能高于某张管线图——这是生成顺序，不代表重要性。
- **两套编号分开放。** `F01`-`F37`
  是管线自己的编号，正文和交叉引用只用它。论文编号（Methods 1–2、Results
  3–13、补充材料
  S1–S24）是给稿件的默认建议，对应关系见上面的索引；论文编号只出现在每张卡片的图注里。
- **文件名保持不变。**
  重命名会牵动代码、图索引的登记表，以及你自己读取这些文件的脚本，所以上面这些
  F 号是唯一在用的编号。`figure_index.png`
  给每张缩略图标的是文件名加一句简短说明。

### 3.2 为论文选图

> **仅供参考。**
> 下面的分法是起点，不是规定；具体选哪几张取决于你论文要讲的内容和期刊的限制。

索引里”论文图”一列已经按这个默认建议填好：

- **Methods 正文（2 张图）。** F01（图
  1）——展示管线*是什么*：各阶段、计数、最终分类构成。F22（图
  2）——展示清洗*做了什么*：非破坏性，只改动了确认的输入错误。这两张图正好回答审稿人最先问的两个问题（“你做了什么？”和”改动有多大？“），不带多余信息。
- **Results 正文（从 11 张里挑 3–5 张）。** F24（图 4，TST
  分布）作为数据质量的锚点； F29/F30（图
  9–10，感知偏差）如果自报值与计算值的一致性是故事的一部分；F35 （图
  11，工作日 vs 周末）或 F36（图 12，TIB
  构成）如果时间规律性/构成很重要；F37 （图
  13，相关矩阵）如果你引用了指标之间的相互关系。正文里最好不要超过五张——
  其余的放进补充材料里读起来更舒服。
- **补充材料（其余全部）。** 所有 `pipeline_cleaning/`
  图（F02-F16、F17-F21）构成审计轨迹：把它们放进一个标题为”数据质量与清洗审计”的补充材料里，在
  Methods 里用一句话统一引用（“完整审计轨迹见补充材料

#### F01 · 管线记录流

**文件** `pipeline_cleaning/F01.png` — 生成于
`sleep_visualization.R:940`

**论文用途** Methods，图 1

**每部分是什么意思** 5 个阶段的垂直流程图，每个阶段都自解释： Raw
Load（全部日记条目）→ Parsed（有时间戳的条目）→ Auto-Corrected （AM/PM +
顺序修正）→ Manual-Corrected（人工审查修正）→ Final Valid
（可用于分析）。每个方框 = 记录数 +
占总数的百分比；两个修正阶段还额外显示参与者人数。

图右侧的图例按每一类列出条数和一行说明；完整定义如下：

| 类别 | 含义 |
|----|----|
| Not Reported | bed / sleep / awake / getup 任一时间缺失 |
| Error (Reviewed) | 顺序被破坏（不满足 `bed ≤ sleep ≤ awake ≤ getup`）、`sleep = awake`、某段间隔 \> 7 小时，或睡眠跨度 \> 24 小时——审查后已修正 |
| Equal Time | `bed == sleep` 和/或 `awake == getup`（差值 \< 0.01 小时，约 36 秒）且顺序完整——一种良性的填表习惯。（`sleep == awake` 是 ERROR，不是这个。） |
| Unusual (Accepted) | 顺序完整但有一段间隔 \> 3 小时（bed→sleep 或 awake→getup）——奇怪但可能，审查后原样保留 |
| Clean | 顺序完整，没有超过 3 小时的间隔 |

图上每一类旁边都印着这些标准（按上面的顺序，第一个匹配的生效），不看本页也能读懂。

先匹配到的类别优先，顺序如上。还有第六类 Reasonable
unusual：审阅者标为合理的异常模式，算作有效。副标题给出进入分析的原始记录百分比，以及至少有一次修正的参与者人数。

**健康外观** 流程从原始记录到有效记录平缓收窄；侧边说明里 Clean
最大，Error 加 Unusual 合计不到约
5%；两个修正阶段的数字都很小——说明只有确实出错的记录被修正，其余数据按填写原样保留。

**异常 →** Error/Unusual 占比很大，通常是上游的 AM/PM
混淆或解析问题，而不是真有成千上万个坏夜晚；已知有错误的数据里修正数几乎为零，则说明检测漏掉了记录。

**精确规则**

- **统计的是什么。** 每一行原始日记记录算一条（真实运行里是 13,990
  条）。五个方框是依次经过的阶段：全部载入、有时间戳的记录、被规则修正的记录（AM/PM
  和顺序修复）、被人工修正的记录、可用于分析的记录。所有百分比都以原始总数为分母。
- **侧边的分类怎么来的。**
  每条最终记录恰好落入一类，自上而下依次判断：未报告、错误、等时、少见、干净，先匹配到的生效。确切规则在”术语与定义”里，图上每一类旁边也印着。
- **最下面那行**（“x%
  的原始记录进入分析”）是四个时间戳都齐全、因而算得出睡眠指标的记录占原始记录的比例。
- **有修正的参与者**是至少有一条记录被修正的参与者数，分母是全部参与者。

**常见问题**

为什么 Equal Time 不算错误？

入睡潜伏期为零（或一醒就起床）是合理的报告。管线把 `error`
留给写出来就不可能的记录：顺序被打破，或零睡眠。

如果两对都相等（bed = sleep 且 awake = getup）呢？

仍然是 `equal_time_ok`，记作 `both_equal`。

0.01 小时对审查者意味着什么？

相差不到约 36
秒的两个时间戳算同一个。这个容差只用来吸收浮点数舍入，不会掩盖真实差别。

为什么将近 80% 的记录是”未报告”？这是问题吗？

意思是这些行至少缺了四个时间中的一个（比如那天没填日记）。管线从不猜测缺失的时间。是否算问题，取决于你的研究设计和预期的回收率——拿它和你的预期比一比。

图里”Error (Reviewed)“只有 3 条，但 F22 显示修正了 77 条，哪个对？

都对。F01 给最终数据分类：修好的错误不再是错误，所以这一类只剩 3 条。F22
数的是一路上被改动过的记录。

Unusual 记录是按”间隔异常”这条规则挑出来的，不是随机样本。它们不必长得像
Clean，不一样也不代表它们是错的。

人工修正的曲线在最短和最长两端有额外的小包，这是问题吗？

人工修正的记录本来就是因为坏了才被挑出来的，所以极端时长在其中占比偏高。值得逐条打开看，但光凭这些小包不能说明修正有错。

#### F05 · 标记共现图

**文件** `pipeline_cleaning/F05.png` — 生成于
`sleep_visualization.R:1691`

**论文用途** Supplement，图 S4

**每部分是什么意思**
热力图，显示两个质量标记在同一条记录上同时出现的频率，基于最终修正后的数据。两条轴列出同样的四个标记；每个格子是两个标记都为
TRUE
的记录数，数字写在格子里，颜色随计数增大由浅变红（平方根刻度，图例为”Co-occurrence
Count”）。

| 轴标签 | 标记 | 触发条件 |
|----|----|----|
| `poor_efficiency` | `flag_poor_efficiency` | 睡眠效率低于 `classification.flag_severity.poor_efficiency_threshold_pct`（默认 70%） |
| `high_sol` | `flag_high_sol` | 入睡潜伏期高于 `classification.flag_severity.high_sol_threshold_hours`（默认 1 小时） |
| `high_waso` | `flag_high_waso` | 睡后觉醒高于 `classification.flag_severity.high_waso_threshold_hours`（默认 1.5 小时） |
| `sleep_calculation_issue` | `flag_sleep_calculation_issue` | 计算得到的入睡潜伏期与自评的入睡潜伏期相差超过 30 分钟 |

**数字从哪来** 并不是每个标记都基于同一类数值，读图时要注意：

- `high_sol` 用的是**计算得到的**
  SOL，不是自评的：用修正后的上床时间和修正后的入睡时间，`time_sleep_corrected − time_bed_corrected`，换算成分钟后再除以
  60。
- `high_waso` 用的是**自评的** WASO 估计值（参与者填写的分钟数，除以
  60）。
- `sleep_calculation_issue` 比较计算 SOL 与自评
  SOL，是唯一看两者差距的标记。

**怎么读一个格子** 在两条轴上找到两个标记，读格子里的数字。例如
`high_sol` 与 `sleep_calculation_issue` 交叉的格子，数的是既有较长的计算
SOL、又与参与者自己填的 SOL 对不上的记录。这些记录最值得先看，因为长 SOL
可能来自时间戳问题，而不是真的入睡慢。每一对都出现两次（见精确规则），读哪一份都行。

有两个问题常被问到，下面的常见问题有完整回答：[高 SOL
是自评的还是计算的？](#fig11-q-sol)以及 [`sleep_calculation_issue`
是什么意思？](#fig11-q-calc)

**健康外观**
大多数格子颜色很浅或没有，也没有哪一对特别突出。出现少数中等深度的格子是正常的：计算出的入睡潜伏期很长会拉低睡眠效率，计算
SOL 与自评 SOL 差距很大，也自然会伴随高 SOL 标记。

**异常 →**
某一格明显比其他格深得多，或多数组合同时偏深，说明同一个原因同时触发了多个标记（常见于许多记录共有的时间戳问题，或阈值本身就互相重叠）。去看深色格子背后的记录，先从
`high_sol` × `sleep_calculation_issue` 看起。

**精确规则**

- **数的是什么。**
  只使用四个标记列都有非缺失值的记录（`complete.cases`）。每个格子是这些记录中两个标记都为
  TRUE 的条数。
- **对称矩阵。** A 与 B 的计数等于 B 与 A
  的计数，所以每一对都画了两次（对角线两侧各一次），读一侧即可。对角线（标记与自己）不画。
- **空白格子。** 计数为 0 的组合不画，而不是画成一个 0
  的格子。空白表示”从未同时出现”，不是”缺失”。
- **颜色刻度。**
  平方根刻度，避免少数很大的计数把小计数压平。颜色只能粗略比较；确切数量请读格子里的数字。
- **数据来源。** 最终修正后的数据（`clean_df`），与 F03、F04 同源。
- **没有使用的标记。** `flag_duration_extreme` 和三级的 `flag_severity`
  标签（Clean/Minor/Major —— `flag_severity`
  的定义）不在这张图里：它们都不是可以两两计数的普通 TRUE/FALSE 标记。
- **何时跳过。**
  四个标记列中完整数据少于两列，或没有任何一对标记在同一条记录上同时出现，这张图就不画，原因会写在
  `figure_index.png` 的红色区块里。

**常见问题**

这里的”高 SOL”是自评的还是计算的？

**计算的。** `flag_high_sol` 用的是
`sol_h = self_diffcalc_sol_minutes / 60`，其中
`self_diffcalc_sol_minutes`
是修正后的入睡时间减去修正后的上床时间（分钟）。参与者自己填的
SOL（`duration_totalmin_sol_estimate_am_mincalc`）**不**用于这个标记，只通过
`sleep_calculation_issue`
进入这张图，该标记比较的就是两者。相反，`flag_high_waso` 用的是自评的
WASO 估计值。

不要把它和第 8 步的 `SELF_REPORTED_FLAG`（文件
`flagged_records_self_reported.csv`）混淆。那是另一个标记：标出自评数值看起来不合理的记录，例如自评
SOL 超过 120 分钟（或 TST/TIB 比值很低）。它不属于这张图。

sleep_calculation_issue 是什么意思？

当计算 SOL 与自评 SOL 相差超过 30 分钟时，`flag_sleep_calculation_issue`
为 TRUE。它只看 SOL，不看 WASO
或总睡眠时间。尽管名字里有”calculation”，它**不**表示计算有
bug；它的意思是关于”花了多久才睡着”的两种说法对不上。常见原因有：时间戳错误、SOL
填错（例如在分钟栏里填了钟点），或一般的感知偏差。

还有两点要知道：任何一个值缺失时该标记为 FALSE（不是
NA），所以”没有被标记”并不表示两者一致。另外，30
分钟的界限写死在代码里（`sleep_visualization.R` 的
`add_quality_flags()`），不是配置项，也没有出现在阈值页面上。

high_sol 的格子很深，是不是说明参与者真的入睡很慢？

不一定。在验证数据里，计算 SOL 与自评 SOL 最多可相差约 75
分钟（见[验证方法学](https://cyracaid.github.io/sleepdiary-cleaner/articles/validation-methodology-zh.md)），所以高
SOL
标记分不清是真的入睡很久，还是两种来源之间的一般性分歧。这些标记是供人工复核的描述性指示，不是自动的错误信号。

它们在这次运行中的计数为 0。从未同时出现的组合不画。

为什么我的输出里没有这张图？

要么完整数据的标记列少于两列，要么没有任何一对标记同时出现。原因会写在
`figure_index.png` 顶部的红色区块里。

#### F07 · 相邻时间戳间隔

**文件** `pipeline_cleaning/F07.png` — 生成于
`sleep_visualization.R:1964`

**论文用途** Supplement，图 S6

**每部分是什么意思** 相邻日记事件（bed→sleep、sleep→awake、
awake→getup）之间的间隔小时数直方图，用的是**修正前的原始时间**。负间隔
= 后一个事件的时钟时间早于前一个。0 处有竖直参考线。

**健康外观** 多数间隔落在 +0.5 到 +2

**异常 →**
负间隔占很大比例，说明普遍存在顺序错误，规整步骤会把它们翻转过来；在 ±12
小时附近出现两个堆，则指向 12 小时钟面的 AM/PM 习惯。

**用文字举例怎么读** Sleep -\> Awake
面板里红色带的计数很高，说明很多原始行里的入睡时间和醒来时间看起来互换了或
AM/PM
反了；规整步骤和人工复核随后会处理它们。某个面板的计数接近零，说明这对事件上这种模式很少见。这个数字说的是原始填写中这种模式出现的频率，不是现在还有多少没解决（见下面的常见问题）。

**精确规则**

- **间隔是什么。** 对相邻的三对时间——bed 到 sleep、sleep 到 awake、awake
  到
  getup——间隔是后一个时间减前一个时间，单位小时，在原始（已解码）时间上计算，还没有做任何修正。
- **负间隔** 表示后一个事件的钟点比前一个事件还早（比如同一行里醒来是
  01:00，入睡却是 23:00）。这是顺序错误或 12 小时制 AM/PM
  弄反的原始特征。
- **红色色带** 标出 −3 到 −6
  小时的间隔，这个范围定义了验证工作里的”AM/PM
  解码或字段互换候选”；带内的数量印在带上。
- **红色 `n=` 标签是什么。** 每个面板（Bed -\> Sleep、Sleep -\> Awake
  (TST)、Awake -\>
  Getup）各有一个标签。它是该面板中原始（修正前）间隔为负、且大小在 3 到
  6
  小时之间（两端都含）的记录数。它由当前这次运行的数据实时统计，不是手写的数字，所以会随每次运行、每个数据集而变；这是有意为之，保证标签不会和真实数量脱节。
- **这个带从哪来。** 3 到 6
  小时的范围是验证工作里固定下来的定义（`validation/derive_timegap_candidates.R`）：这种大小的反向间隔，是
  AM/PM
  解码错误或字段互换的典型特征。它是用来找候选的定义，不是测得的错误率。
- **带外的是什么。** 反向不到 3 小时（小幅互换）或超过 6
  小时的间隔，不计入
  `n=`，由其他规则处理（上面的形状说明写了哪种修复对应哪种模式）。
- **加总。**
  各面板的数字加起来是候选总数，同一条记录可以出现在不止一个面板里。
- **怎么读形状。** 大约 −1 到 −3
  小时的负值堆，指向顺序互换（由互换步骤修复）；在 ±12
  小时附近出现两个堆，指向把 PM 时间填成了 AM（由 12
  小时翻转步骤修复）。

**常见问题**

为什么在修正之前画？

因为它要显示原始填写是什么样。修正之后负间隔大多没了，画出来就看不到管线解决的问题了。

为什么三个面板的坐标不一样？

每一对时间的典型大小不同：bed→sleep 和 awake→getup
的间隔通常在一两个小时以内，而 sleep→awake 是整晚（约 6–10
小时）。每个面板按自己的数据缩放。

红色带里的数字，说明有这么多记录是错的吗？

不是。这个数字数的是*候选*，只按原始间隔的大小（为负、3 到 6
小时）筛选。其中有些是真实的长间隔，或是习惯性按”反方向”填写的记录；哪些是错误，由清洗规则和人工复核决定，不由这个标签决定。

它也只是历史的一张快照：原始填写中这种模式出现得有多频繁。它不显示修正和复核之后还有什么没解决。要看这个，请见[人工复核循环](https://cyracaid.github.io/sleepdiary-cleaner/articles/interpreting-output-zh.html#s-3)里的复核状态表，以及[运行汇总](https://cyracaid.github.io/sleepdiary-cleaner/articles/interpreting-output-zh.html#s-4)里的最终记录分类。

**论文用途** Supplement，图 S7

**每部分是什么意思**
来自合成错误注入基准的热力图。每一行是一种被故意注入干净记录的错误类型；每一列是管线对它做了什么：`CORRECT`（修对了）、`FLAGGED_UNRESOLVED`（检测到但交给人处理，没有自动修）、`MISREPAIRED`（修错了）、`MISSED`（没检测到）、`NO_MATCH`。每个格子是该错误类型的记录中出现这种结果的百分比。副标题写明了注入的行数和类别数。

**健康外观** 每一行的颜色几乎都落在 `CORRECT` 或
`FLAGGED_UNRESOLVED`——错误要么被正确修好，要么被检测到并交给人——而
`MISREPAIRED`、`MISSED`、`NO_MATCH` 接近
0。有些错误类型只会被标记、从不自动修（比如填错字段），这是设计使然：管线对不能安全修复的东西选择标记，而不是猜。

**异常 →** `MISREPAIRED`
有颜色，说明自动修错了——比不动这条记录还糟。`MISSED`
有颜色，说明这种错误根本没被检测到。

**精确规则**

- **数据从哪来。**
  合成错误注入基准（`validation/synthetic/results/detection_outcomes_v4_current.csv`）：把已知的错误注入干净数据，再在结果上跑管线。因为正确答案是已知的，每个结果都能被打上标签。
- **一个格子是什么。** 对某种注入的错误类型，`n` 是注入的行数；格子是
  `count / n × 100`。所以每一行加起来约为 100%。
- **五种结果。** `CORRECT` 修对了；`FLAGGED_UNRESOLVED`
  检测到但交给人处理、没有修；`MISREPAIRED` 修错了；`MISSED`
  没检测到；`NO_MATCH` 这条注入的行没能和管线输出里的某一行一一对上。

**常见问题**

为什么合成注入的图会放在 QC 文件夹里？

它是检测数字有意义的证据：检测器是拿已知的真值来检验的，而真实数据里”正确答案”是不可知的。

FLAGGED_UNRESOLVED 算失败吗？

不算。它表示管线发现了问题，但不想猜着去修，把决定留给人。对某些错误类型（比如值填到了错误的字段），这正是设计的行为。

哪种颜色最让人担心？

MISREPAIRED。自动修错比不动这条记录更糟，因为它悄悄改了数据，没人察觉。其次是
MISSED：错误留在数据里没被发现。

这张图能告诉我真实数据里有多少错误吗？

不能。它是在故意放进错误的合成数据上做的测试。它告诉你每个检测器有多可靠，而不是你自己的数据里有多少错误。

#### F09 · 阈值 vs 测量噪声

**文件** `pipeline_cleaning/F09.png` — 生成于
`sleep_visualization.R:2084`

**论文用途** Supplement，图 S8

**每部分是什么意思**
横向柱状图，每根柱子对应一个能和自报值对照检验的清洗阈值（SOL 和 WASO
的阈值；没有自报对应值的阈值，比如睡眠效率，不画，副标题会写明省略了几个）。柱子长度
= 阈值 ÷ 测量噪声，其中噪声是自报值与管线根据时间戳算出的值之间
Bland-Altman 95% 一致性界限的半宽。虚线标出 2×（临界）和 3×（安全）。

**健康外观** 柱子在 3×
或更长：阈值远高于自报值和计算值之间的正常分歧，所以被它标记的记录，不太可能只是因为测量噪声而被标记。在
2× 到 3× 之间属于临界。

**异常 →** 柱子短于
2×，说明阈值落在典型的测量分歧之内：它标记的记录可能仅仅是噪声造成的，所以把这个标记当作”值得看一眼”的提示，而不是出错的证据——并考虑调高阈值。

**精确规则**

- **每根柱子是什么。**
  一个清洗阈值除以测量噪声。只画能和自报值对照检验的阈值（SOL 和 WASO
  的阈值）；副标题会写明省略了几个别的，比如睡眠效率。
- **“噪声”指什么。**
  自报值和管线根据时间戳算出的值永远不会完全一致。它们典型的分歧，就是
  Bland-Altman 95% 一致性界限的半宽，这就是噪声。
- **怎么分级。** 至少 5× 保守，至少 3× 安全，至少 2× 临界，低于 2×
  落在噪声之内。虚线在 2× 和 3×。
- **用的是现场数字。** 由
  [`validate_thresholds()`](https://cyracaid.github.io/sleepdiary-cleaner/reference/validate_thresholds.md)（`R/bland_altman.R`）用本次运行的数据计算，不是来自合成基准。

**常见问题**

为什么要把阈值和噪声比较？

比测量噪声还小的阈值检测不到任何真实的东西——它只会标记纯噪声。这张图显示每个阈值高出噪声多少。

有一根柱子低于 2×，一定要改阈值吗？

不一定。它的意思是被这个阈值标记的记录，可能仅仅因为噪声就被标记了，所以把那些标记当作”去看一眼”的提示，而不是出错的证据。调高阈值是一种办法；保留阈值、再去审查被标记的记录是另一种。

为什么没有睡眠效率和 TST/TIB？

它们没有可对照的自报值，所以估计不出噪声。副标题会写明省略了几个阈值。

> **Figure S8.** 每个清洗阈值除以 Bland-Altman
> 测量噪声（自报值与计算值之间 95% 一致性界限的半宽）。虚线标出

#### F17 · 时间顺序反了的夜晚，按机制

**文件** `pipeline_cleaning/F17.png` — 生成于
`sleep_visualization.R:3296`

**论文用途** Supplement，图 S20

**标题与副标题**
标题：*时间顺序反了的夜晚，按机制*。副标题几行：这张图回答什么（四个时间不满足
就寝 ≤ 入睡 ≤ 醒来 ≤ 起床 时，是哪一种失误）、一根条怎么读、以及数量 N。

**每部分是什么意思**
一晚的四个自报时间（上床、入睡、最终醒来、起床）可能以哪几种方式出现顺序错乱，每种方式一行，由
[`classify_reversals()`](https://cyracaid.github.io/sleepdiary-cleaner/reference/classify_reversals.md)
得出。每一行都会画出来，没有病例的也画，所以没有病例的机制显示为
0，而不是消失。柱长是夜晚数，右列是它占全部顺序错乱夜晚的比例。不属于所列形态的归入”Other
forms”。

| 颜色 | 含义                                                     |
|------|----------------------------------------------------------|
| 深灰 | 两个时间互换（上床与入睡，或醒来与起床）                 |
| 浅蓝 | 一个时间差 12 小时（通常是 AM/PM 手滑）                  |
| 深蓝 | 两个时间一起挪了 12 小时（整段）                         |
| 橙色 | 明显有问题：醒来早于上床、间隔在舍入范围内、起床值不可能 |
| 灰蓝 | 没有简单解释，或不在所列形态内                           |

**健康外观**
占完整夜晚的一小部分（几个百分点），大部分落在最上面几行：两个时间互换、入睡时间早了
12 小时，是修正步骤自己能修好的形态。

**异常 →** “Bed time 12 h early”或”Whole night shifted 12
h”的柱很长，不是图的问题：自动修正很少能修好这两种，这些夜晚要靠审查表。“No
simple explanation”的柱很长，说明这些顺序错乱不是 AM/PM
或顺序上的习惯，值得回头看原始输入。

**精确规则**

- **算什么。** 四个时间都齐全、且顺序违反 上床 ≤ 入睡 ≤ 最终醒来 ≤ 起床
  的夜晚。副标题给出数量、完整夜晚数和百分比。
- **一行怎么分配。**
  取能恢复顺序、又让这一晚保持合理的最小改动：互换两个字段，把一个字段挪
  12 小时，或把两个字段都挪 12
  小时。没有改动能解释的夜晚，按它明显出了什么问题来归类。
- **不可能是真的起床值。**
  这些夜晚也计入图里，但在副标题里单独说明，因为它们是字段取值问题，不是顺序问题。
- **不改任何数据。** 这张图读的是修正前的列，不会改动数据。

**常见问题**

顺序反了的夜晚，就是管线标记的错误吗？

#### F18 · 钟点规则的处理结果（SOL / WASO）

**文件** `pipeline_cleaning/F18.png` — 生成于
`sleep_visualization.R:3358`

**论文用途** Supplement，图 S21

**标题与副标题** 标题：*被读成钟点或误填时长的 SOL / WASO
条目*。副标题几行：这张图回答什么（第 6.5
步对每条被重新解读的条目做了什么）、一根条怎么读、以及数量 N。

**每部分是什么意思** 对区间解析器重新解读过的 SOL / WASO
条目（按分:秒读，或 `dd:00`），每种第 6.5
步钟点规则的处理结果一条横条。条末数字是条数；颜色是字段（蓝 SOL，橙
WASO）。数据来自
`output/duration_clock_rule_log.csv`，里面逐条列出了每条做了什么。

| 横条 | 含义 |
|----|----|
| 按分钟保留 | 像 `5:00` 这样的填法，按 5 分钟读，不改 |
| SOL 按钟点重算 | 所填时间贴近本人入睡时间，且在上床之后；SOL = 所填时间 − 上床时间 |
| 置缺失 | 所填的是上床钟点（SOL），或 WASO 像钟点；原文保留 |
| 留给人看 | 像钟点但规则判不了；值保持解析结果，仍被标记 |

**健康外观** 大部分是”按分钟保留”，少数重算，置缺失很少。

**异常 →**
“留给人看”很长，说明很多条目落在规则的容差和窗口之间；这就是要人读的清单。

**精确规则**

- **算什么。** 只算区间解析器已经重新解读过的条目——按 MM:SS 规则或
  `dd:00` 规则读过的那些，记录在 `*_correctionsmade` 或 `*_ambig`
  里。人工已经改过的行不计入；每个计入的条目都在
  `output/duration_clock_rule_log.csv` 里有一行。
- **判断顺序。** 不以 `:00` 结尾的文本不可能是”分钟写进了小时位”，会落到
  WASO 或 SOL 分支。SOL 分支把输入的时间与本人在那晚的就寝、入睡时间放在
  12 小时表盘上比（因为没填 AM/PM），依次是：输入时间与入睡时间相差 ≤ 5
  分钟、且在就寝时间之后 0–60 分钟内 →
  重算；离就寝时间比离入睡时间更近、且相距 ≤ 15 分钟 → 置缺失；其余 →
  留给人看。
- **WASO 从不重算。** 钟点能换算成
  SOL（输入时间减就寝时间），但换算不成”时长”，所以看起来像钟点的 WASO
  一律置缺失，留在审查队列里。
- **默认值。** `duration_clock_rule.tolerance_min` = 5、`.window_min` =
  60、`.near_min` = 15，三个都是配置键。
- **什么都不删。**
  “置缺失”只清掉算出来的分钟数：原始文本仍在输入列里，改动写进
  `*_correctionsmade`，第 8 步照样标记这一行。

**常见问题**

为什么同样的输入值，不同晚上落进不同的条？

因为归类看的是本人那一晚的时间，不是文本本身：`23:30`
在某一晚是合理的入睡时间，在另一晚就是就寝时间。

“置缺失”会把参与者填的答案丢掉吗？

不会。文本留在原始输入列里，改动逐行记录；这一晚只是没有算出来的 SOL 或
WASO，审查表里会列出来。

**论文图注**

> **Figure S21.** 看起来像钟点或误填时长的 SOL 和 WASO
> 条目，按钟点规则对每条的处理分类。N 见副标题。

#### F21 · 顺序颠倒的夜晚，改正前后

**文件** `pipeline_cleaning/F21.png` — 生成于
`sleep_visualization.R:3530`

**论文用途** Supplement，图 S24

**标题与副标题** 标题：*本研究里顺序颠倒的夜晚，改正前后*。两栏。A
栏副标题：改正前有多少夜晚顺序颠倒（条的长度），其中多少由算法改对、多少经人工审核改对、多少没有。B
栏副标题：每个研究日里顺序错乱的夜晚占多少，并与总体比例对照。

**每部分是什么意思** *A 栏：* 每个机制族一条（分类同
F17，合并成族）。条的长度是改正前顺序颠倒的夜晚数；颜色是这些夜晚在最终数据里的状态：算法改对、人工审核后改对、顺序对但不合理、仍然颠倒、没有改后值。读的是本次运行最终的
`time_*_corrected` 列，并用 `correction_type` 和 `manually_corrected`
区分是谁改的。“顺序对”不等于改成了真值。*B 栏：*
每个研究日一条：当天四个时间齐全的夜晚里，顺序错乱的百分比，标签是错乱夜晚的数量，虚线是总体百分比。图上不画任何统计检验。

**健康外观** A 栏：每条几乎全是蓝色或橙色。B 栏：各条接近虚线。

**异常 →** 条末的朱红：这些夜晚在最终数据里仍然颠倒，需要人看。

**精确规则**

- **改正前。**
  [`classify_reversals()`](https://cyracaid.github.io/sleepdiary-cleaner/reference/classify_reversals.md)
  读的是修正前的列（`time_*_am_hhmm_ampm`）；四个时间齐全、且 就寝 ≤
  入睡 ≤ 最终醒来 ≤ 起床 不成立的夜晚才算。这个数就是条长。
- **改正后。**
  同一晚在最终列（`time_*_corrected`）里的状态，下列几种之一。“顺序正常”指
  SOL ≥ 0、TST ≥ 0、起床 ≥ 最终醒来；“合理”再加 SOL ≤ 300 分钟、卧床
  120–960 分钟、TST 30–720 分钟、醒来到起床 0–300 分钟——就是
  [`classify_reversals()`](https://cyracaid.github.io/sleepdiary-cleaner/reference/classify_reversals.md)
  用的那套宽松界限，所以才会出现”顺序正常但不合理”。
- **机制族。** F17 的机制类别归并：`swap*` = 两个时间互换；`pm12h` =
  一个时间差 12 小时；`pm12h_x2` = 两个时间一起挪 12 小时；D 或 E
  开头的类 = 明显有问题或无法解释；其余 = 模糊。条按夜晚数排序。
- **一晚只算一个状态。**
  修正后有时间缺失的夜晚记为”没有修正后的值”，不同时算作仍然乱序。
- **谁改对的。**
  顺序正常且合理的夜晚，如果有规则作用在它上面（`correction_type`
  有值）就算算法的，即使人也改过；只有人改过（`manually_corrected`）才算人工审核。这两列缺失时，图退回成单一的”顺序正常且合理”颜色。
- **B 栏。**
  四个修正后的时间齐全算”完整夜晚”；[`classify_reversals()`](https://cyracaid.github.io/sleepdiary-cleaner/reference/classify_reversals.md)
  列出的算”顺序错乱”。第 1–3
  天的条高是一个值得看的模式，不是结论：图里不画检验。
- **它不说的事。**
  改后的时间是不是真值。“改对”指顺序正常且合理，不表示核对过。

**常见问题**

蓝色的比例能当成管线的成功率吗？

蓝色是算法自己改对的，橙色是人在审查里改对的。所以蓝色是这项研究里算法承担的那部分工作，不是找到真值的比率：“改对”指顺序正常且合理，不表示核对过。规则找回真值的频率，要在有已知真值的合成测试（F20）里测。

为什么各族之间的蓝色差这么多？

因为自动修正只对有规则的形态有效：两个时间互换、以及单个字段差 12
小时。就寝时间差 12 小时、整晚挪了 12
小时、醒来早于就寝这三种，要等人读审查表才会变。

#### F22 · 修正影响

**文件** `research_ready/F22.png` — 生成于 `sleep_visualization.R:1094`

**论文用途** Methods，图 2

**用途**
审计修正对数据改了多少、往哪个方向改，回答”清洗有多侵入？“。图的副标题写明了用途，并解释了每个面板怎么读。

**每部分是什么意思** 一行三个面板，标为 a–c：(a) TST
变化量棒棒糖图——每个被修正的记录一行，x = ΔTST（分钟）；(b) SOL
同样画法；(c) 一致性散点图，修正前 TST vs 修正后
TST（全部记录）；下方是修正前后 TST/SOL 均值 ±
标准差的汇总表。图注写明了共修正了多少条、总共多少条记录中的多少条。

| 标记                            | 含义                                   |
|---------------------------------|----------------------------------------|
| ● 橙色                          | 算法修正                               |
| ● 蓝色                          | 人工修正                               |
| ● 灰色，3% 不透明度（仅面板 C） | 未改动的记录——几乎透明，衬在修正点背后 |
| 虚线对角线（面板 C）            | 1:1”无变化”参考线                      |

**没有任何修正时**
如果没有记录被改动（数据本来干净，或人工修正文件没有应用），面板 A–C
都会是空的，所以图上只显示一句话——“No record was changed by a correction
in this
run（本次运行没有记录被修正；无需修正，或人工修正文件未应用）”——加上修正前后的汇总表（此时两行数字相同）。

**健康外观** 大多数点落在虚线对角线上，上面两个面板里的线很短、集中在 0
附近，表里修正前后的均值也很接近。这说明清洗是非破坏性的：它只改了少数记录，而不是整份数据。

**异常 →**
线很长或被修正的记录占比很大，说明修正正在改变真实数据，而不只是修录入错误；修正前后均值明显偏移，则需要追问为什么”修”了这么多。

**精确规则**

- **谁算”被修改”。** 每条记录有一个状态：被人工修正触及过的是
  `manual`，否则被规则改过的是 `algorithmic`，否则是
  `none`。一条记录不会同时是两者；manual 优先。
- **上面两个面板画什么。**
  只画被修改的记录，每条一行，按改动的大小排序。ΔTST = 修正后 TST −
  修正前 TST（分钟），ΔSOL 同理。负的线表示修正把这个值变短了。
- **“修正前”指什么。** “修正前”的值是用原始解析出的时间戳重新算的（TST =
  awake − sleep − WASO，SOL = sleep − bed）；“修正后”是管线最终的数字。
- **散点图**
  把全部记录的修正前（x）对修正后（y）画出来。没改动的记录画得几乎透明，所以在对角线后面形成一条淡淡的带，衬出少数彩色的被修改点。
- **表格** 给出 TST 和 SOL
  修正前后的均值与标准差；图注写明了总共多少条记录里改了多少条。

**常见问题**

为什么大部分数据都落在对角线上？

修正按设计是非破坏性的：只修正确认的输入错误（真实运行中约占 0.6%
的记录）。自报值与计算值之间的差异作为数据保留，不会被抹平。

淡淡的点可以离对角线很远吗？

没改动的记录应该落在对角线上。淡点偏离对角线，说明一条没被标记为修正的记录，它的”修正前”值（用原始时间戳重算）和”修正后”值（管线的最终数字）不一样。这张图说不出原因；请打开那条记录看一看。

为什么很多被修正的记录正好是 ±720 分钟？

720 分钟就是 12 小时。AM/PM 翻转会让一个钟点正好变 12
小时，导出的时长也就正好变 12 小时，所以 AM/PM 修复会堆在同一个长度上。

长长的线说明修正错了吗？

不。大的变化通常说明修掉了一个大的输入错误，比如差了 12
小时。修正对不对是在审查里定的，不是这张图；这张图显示的是改动有多大。

为什么有这张表？

它让你一眼看出”平均值变了吗？“。如果修正前后的均值接近，说明清洗没有让整体数据发生偏移。

SOL 有一小段负值，是错误吗？

**文件** `research_ready/F24.png` — 生成于 `sleep_visualization.R:1190`

**论文用途** Results，图 4

**每部分是什么意思** 总睡眠时间（TST——见前文”术语”）的直方图 + 密度图。

|----------------|------------------------|
| ● 红色平滑曲线 | 密度估计               |
| ● 蓝色实线     | 均值（标注小时数值）   |
| ● 橙色虚线     | 中位数（标注小时数值） |

图下方标题为 “Line shown” 的图例说明了每条线。

这里的 TST
是*增强版*定义：`TST = TIB − SOL − WASO`——不是两个时间戳的原始时钟差值。

**健康外观** 一个峰，中心在 6–8

**异常 →**

- **这里的 TST 是什么。**

  `sleep_duration_h`）。它不是两个钟点的原始差值。
- **几条线。** 蓝色实线 = 均值，橙色虚线 = 中位数，红色 =
  平滑密度；图例”Line shown”写明了它们，两个数值也印在里面。
- **偏度。**
  对睡眠数据来说，均值通常比中位数略高，因为右边有睡得特别久的人形成的尾巴。
- **角落的 `n`** 是算得出 TST 的记录数。

**常见问题**

为什么有两张分布图（F23 和 F24）？

F23 是五个指标的小面板总览。F24 把 TST
单独拿出来，并标出均值和中位数，这是论文里通常的第一张图。

为什么 TST 不是入睡到醒来之间的时间？

因为夜里常常有入睡之后醒着的时间。管线会把这部分（WASO）减掉，所以 TST
只算真正睡着的时间。

我的均值和中位数差很远，这意味着什么？

差距说明分布是偏的：一条很长（或很短）的尾巴把均值从中位数拉开了。看看直方图哪一侧有尾巴，再看
F10（修正前）和 F02（修正后）。

这些曲线包含被人工修正的记录吗？

包含。这是最终修正后的数据，所以被修正的记录按修正后的值计入。

#### F25 · 睡眠时长 vs 卧床时间

**文件** `research_ready/F25.png` — 生成于 `sleep_visualization.R:1245`

**论文用途** Results，图 5

**每部分是什么意思** 卧床时间（从躺下到起床）对睡眠时长（实际睡着的时间
= TIB − SOL − WASO）的散点图。黑线 = 线性趋势；周围的灰带 =
该趋势的不确定范围。虚线对角线 = 不可能出现的 TST == TIB 线。

**健康外观**
点贴近虚线（1:1）分布，卧床时间越长散得越开（人会躺着醒着）；没有 TST
超过卧床时间的点，那是不可能的。

**异常 →** 点落在线上方（TST \> TIB），说明时长计算出了错，比如没减去
WASO；点云毫无形状，说明 TIB 和 TST 脱钩了，通常是解析问题。

**精确规则**

- **画的是什么。** 卧床时间（x）对总睡眠时间（y），只画卧床时间低于 24
  小时、TST 在 0 到 20 小时之间的记录。颜色是数据质量类别。
- **不可能线。** 虚线对角线是 TST = TIB。因为 TST = TIB − SOL −
  WASO，任何有效的点都不会在它上方。
- **趋势线** 是普通的直线拟合，带着不确定性范围；副标题印着相关系数
  `r`。
- **视野** 为了好读，两个坐标轴都截在 0–16
  小时；统计用的是范围内的全部点。

**常见问题**

虚线上方的点意味着什么？

那意味着睡的时间比卧床时间还长，这是不可能的。它指向时长计算的问题，比如没有减去
WASO。健康的数据里不应该有这样的点。

为什么卧床时间越长，点云散得越开？

卧床时间越长的人，常常有一部分时间是醒着的，所以睡眠并不像卧床时间增长得那么快。这是正常的散开，不是噪声。

我看到虚线上方有几个点，该怎么办？

它们按记录来说是不可能的（睡的时间比卧床时间还长），通常是解析出了差错或时间戳有问题。在数据里筛选
`sleep_duration_h > time_in_bed_h` 就能找到它们，再逐条手工检查。

为什么坐标轴截在 16 小时？

为了保持图好读。有几个极端点在视野之外，但仍然算在统计里。

> **Figure 5.**
> TST（小时）对卧床时间（TIB，小时）的散点图，带平滑趋势线和恒等参考线。由于构造上

附近，只有一小段尾巴。因为这两个量是不同的时间窗口，这主要说明夜间清醒和醒后赖床之间差多少，而不是人们报告得有多准。

**异常 →**
尾巴很长，说明很多参与者的夜间清醒时间和醒后赖床时间差距很大。这有信息量，不是错误；只有怀疑填写有问题时，才去查
WASO 时长的修正。

**精确规则**

- **这两个值不是同一件事。** 这里的客观值是
  `time_getup_corrected − time_awake_corrected`，单位分钟——最终醒来之后在床上待的时间。主观值是参与者报告的夜间清醒时间（`duration_totalmin_waso_estimate_am`，以”时:分”格式写的才会读取）。
- **所以这个差距不是单纯的报告误差。**
  两个数字覆盖的是不同的时间窗口；图的副标题写明了这一点。这种不一致是有信息量的，不是需要修的东西。
- **构造和 F29 相同。** `bias = |客观 − 主观|`，取两个值都存在的记录，x
  轴 0–200 分钟，虚线参考在 15 和 60 分钟。

**常见问题**

为什么要比较两个不同的东西？

管线没有夜间清醒的另一种直接度量，所以能用时间戳得到的最接近的量，是最终醒来到起床之间的时间。图里明确写了窗口不同；它是一致性检查，不是验证。

这里差距大，说明日记有错吗？

不。一个人夜里可能长时间醒着，但起床很快；也可能只醒一次却赖床很久。两种情况差距都会很大，而两个数字都没有错。

为什么用的记录比 F29 少？

只有自报 WASO 写成”时:分”格式的行才能被读取，所以有些行会被丢掉。

#### F35 · 睡眠规律性——工作日 vs 周末

**文件** `research_ready/F35.png` — 生成于 `sleep_visualization.R:3147`

**论文用途** Results，图 11

**每部分是什么意思** 两个并排面板——**左 = 就寝时间，右 =

箱线图。

**使用的列** 就寝时间 = `time_bed_corrected`（校正后的”上床”时间戳，即
`time_bed`）；起床时间 =
`time_getup_corrected`（校正后的”离床”时间戳，即
`time_getup`）。两者都是流水线生成的列，不是原始日记列。就寝时刻早于中午的小时数会
+24，所以 y 值大于 24 表示过了午夜（如 26 = 02:00）。

**健康外观** 周末的就寝时间比工作日晚约 0.5–1 小时，起床晚约 1
小时，其余形状相似——这是典型的、幅度不大的周末偏移。

**异常 →** 工作日和周末的分布完全一样，说明 `day_type`
分错了，或日期被丢掉了；周末偏移特别大，则是社交时差，值得作为一个发现来报告。

**精确规则**

- **用的是哪些列。** 就寝时间来自 `time_bed_corrected`，起床时间来自
  `time_getup_corrected`。两者都是管线生成的修正后时间戳，不是原始日记列。
- **工作日还是周末。**
  按就寝时间戳所在的日历日判断：周六、周日是”Weekend”，周一到周五是”Weekday”。午夜之后的就寝时间带的是第二天的日期。
- **大于 24 的小时数。** 中午之前的就寝小时数会加 24，所以 y 值大于 24
  表示过了午夜（26 = 02:00）。
- **画的是什么。**
  每种日型一把小提琴加一个箱线，分别画就寝时间和起床时间；黑点是中位数。

**常见问题**

凌晨 02:00 的就寝算哪一天？

算就寝时间戳上的那一天。经过管线对午夜的处理，周日凌晨 02:00
的就寝带的是周日的日期，所以算周末的夜晚；周五夜里 01:00 算周六。

周五晚上算周末的夜晚吗？

只有就寝时间过了午夜才算，因为那时带的是周六的日期。周五 23:30
就寝算工作日。这直接来自上面的规则，和其他研究比较时值得记住。

为什么 y 值会超过 24？

这样刚过午夜的就寝时间（比如 01:00）就紧挨着
23:00，而不是跑到坐标轴的最下面。25 表示 01:00。

周末偏移多大算正常？

一个小的偏移——周末晚最多约一小时——是常见的模式。大得多的偏移是社交时差，值得作为一个发现报告。

#### F36 · 睡眠构成——TIB 拆分

**文件** `research_ready/F36.png` — 生成于 `sleep_visualization.R:3200`

**论文用途** Results，图 12

**每部分是什么意思**
卧床时间构成的堆叠柱状图；图的副标题给出了每个缩写的定义：TIB =
TST（总睡眠时间——真正睡着的部分）+ SOL（入睡潜伏期——入睡过程）+
WASO（睡后觉醒——夜间醒着的部分），以占比形式呈现。

**健康外观** TST 是最大的一块（约占卧床时间的 80–90%），SOL 和 WASO
是很小的两段。

**异常 →** SOL 或 WASO 占卧床时间超过
30%，说明睡眠严重碎片化或入睡特别慢；如果出现负的余量，则是时长计算的
bug。

**精确规则**

- **这根条是什么。**
  卧床时间里三个部分各占的平均份额：总睡眠时间（TST）、入睡潜伏期（SOL）和睡后觉醒（WASO）。对每条记录，三部分除以它们的和，再把这些份额在记录之间取平均。
- **恒等式。**
  `TIB = TST + SOL + WASO`，所以三段正好填满整根条，没有余量；任何极小的缝隙都是舍入。
- **包含哪些记录。** 三个值都有、且 TST 大于 0
  的记录；副标题给出了数量。

**常见问题**

这是汇总分钟数的平均，还是每条记录份额的平均？

每条记录份额的平均：每条记录权重相同，不管它多长。汇总版本（所有记录每部分的总分钟数）会让更长的夜晚权重更大，结果可能略有不同。

为什么 SOL 和 WASO 这么小？

多数夜晚里，入睡和夜醒只占卧床时间的一小部分，所以 TST 占主导。SOL 或
WASO 那段很大，说明那些记录睡眠碎片化或入睡很慢。

为什么用一根条而不是饼图？

一根条便于把各段并排比较，小的段也读得清楚，而饼图会把小块挤在一起。

> TIB = TST + SOL + WASO。健康构成中 TST 占 TIB 的 80–90%。

某个指标的定义被改了，或者单位混了（比如分钟和小时）。在解读这张图之前，先检查喂给那个指标的列。
